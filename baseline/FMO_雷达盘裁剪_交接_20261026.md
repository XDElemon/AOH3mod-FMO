## 0. 一句话现状

地图上的范围盘（蓝＝探测/雷达，红＝防空火力）需要"叠放 + 裁剪"才能都看见；
**v88 的 CPU 裁剪仍有两类真机错误**：大蓝盘在左侧时小蓝盘整块消失、大蓝盘在右侧时形状错乱。
离线模拟器**复现不出**这两种现象，说明失败点不在几何模型里，而在于真机的取数/绘制路径。

## 1. 需求口径（用户三次澄清后的定稿）

1. **红圈默认压在蓝圈之上**。
2. **半径小的盘压在上面**（大的先画）——否则小盘会被大盘埋掉。
3. 特例：防空阵地这种"蓝圈比红圈小"的情况，**小蓝圈压在该红圈之上**。
4. 但当这个小蓝圈被**另一个更大的蓝圈**覆盖时：
   - **被覆盖的那部分**要退到红圈之下（让红色露出来）；
   - **没被覆盖的部分**仍在红圈之上。
5. 明确不要：描边环、半透明混色。

用户认可的目标效果图：`/sdcard/GLG/DSHA/v85_mock_compare.png` 第 ① 张
（大蓝盘 + 红环 + 环内被裁成 "D" 形的蓝 + 露出的红）。

## 3. 当前实现（v88）

### 3.1 文件

| 文件 | 角色 |
|---|---|
| `src/java/.../province/AirDiscQueue.java` | 每帧收集所有盘 → 半径降序排序 → 需要让位的蓝盘按行求差 → 用矩形拼 |
| `src/smali/.../province/AirRect.smali` | 1×1 白纹理 + 纯色矩形填充（`fill(Object,int x,int y,int w,int h,int rgb)`） |
| `src/smali/.../province/ProvinceDrawArmy.smali` | 任务蓝盘改为入库；`end()` 前 `flush` |
| `src/java/.../province/AirRadarBld/AirRadarAD/AirRadarPlane` | 建筑蓝盘 / 防空红盘 / 导弹红盘改为入库 |

### 3.2 算法（伪代码）

```
flush():
  discs = 收集的四类盘（蓝/红类型位 TP）
  稳定插入排序：按 rx 降序
  blues=[]; reds=[]
  for d in discs:
     if 红: 整盘画；reds.append(d)
     else:
        需要裁 = 与任一 blues 相交 且 与任一 reds 相交
        if not 需要裁: 整盘画
        else: 逐行(步长 2px):
             iv = 圆盘在该行的横区间
             blocked = (blues 各行的并集) ∩ (reds 各行的并集)   # 只让位给"红色覆盖"
             画 iv - blocked 的剩余区间（用 AirRect 2px 高矩形拼）
        blues.append(d)
```

### 3.3 关键常量
- 蓝盘色 `0x3333FF`（0.2/0.2/1.0），红盘色沿用 `AirRadarAD/Plane` 的 `0xFF3333`
- 扫描行步长 2px；行宽 <2 跳过
- 盘半径口径：空军基地 200 / 雷达 600 / 反导阵地 300 / 中层反导 2400（蓝）；
  防空红 100 或 130 × `iMapScale(=4)` ⇒ 400/520

## 4. 已经确认并修掉的问题（都是真机证据）

1. **Pixmap.drawPixel 要 RGBA8888**，不是 ARGB（v79 绿椭圆）
2. **压扁的椭圆不能靠旋转贴图**（v79 转动处露底）
3. **带 stencil 的 FBO 在本机不可用**（v84 整帧画空）
4. **矩形 x 多减了一次宽度**（v85 形状错乱）
5. **区间求差收尾**：遮挡区间伸出右端时 `break` 未把 `start=end`，收尾又画回去（v86 "裁剪不生效"）
6. **无条件裁蓝**会在蓝蓝重叠处裁出洞（v85 月牙）——应只裁「蓝盘 ∩ 红盘」

## 5. 未解问题（用户 v88 真机反馈，原文）

> "只要你的大蓝盘在左边，小蓝盘会直接不见；右边的话也一定要大蓝盘包裹住了小蓝盘的圆心才能正常显示，
> 如果大蓝盘没有包裹住小蓝盘的中心，并且大蓝盘在小蓝盘右边，绘制会出问题；甚至效果不像你的图。"

**离线复现失败**：用同一套算法跑的模拟图（`v88_suspect_cases.png`、`v88_case1_sweep.png`）
在"大蓝在左/右"两种排布下都没出现"小蓝整块消失"，说明差异来自真机侧，可能的方向：

- **坐标来源**：`getDrawPosX/Y` 每帧取值，盘的 cx/cy 可能随相机/缩放变化；
  裁剪按"当前帧坐标"计算，而绘制发生在同一个 FBO 里——理论上一致，但**若某帧坐标与绘制用的不同源**就会错位。
- **`rowInterval` 的打包/解码**：目前把区间编码成 `(left<<16)+right` 塞进 int。
  left 为负（盘有一部分在屏幕左侧外）时依赖算术右移，**未在真机验证过**；
  左边界为负正是"大蓝盘在左"的典型场景 → **优先怀疑**。
- **`AirRect.fill` 的 y 语义**：传的是"屏幕顶往下的 y"，内部 `-(y+h)`；与 `Image.draw` 的约定一致，
  但矩形是 1×1 纹理拉伸，**若纹理 filter 是 Nearest 且尺寸非 2 的幂**，放大可能出现偏移（未验证）。
- **绘制批限制**：被裁蓝盘每帧最多产生数百个矩形（2px 行 × 2~3 段），
  极端情况下可能超过 SpriteBatch 单批容量 → 表现可能是"整块消失"。
- **排序稳定性**：Java 的插入排序是稳定的，但**等半径**（例如两个反导省的蓝 300）先后取决于收集顺序，
  可能造成"同一个省这次在上一帧在下一帧"的视觉抖动。

## 6. 下一步建议（按性价比排序）

### 方案 A（最快回到可用）：v83 纯排序，不做裁剪
- 只按半径降序画，红上蓝下看大小；**没有任何洞、错位、消失**。
- 代价：小蓝盘被大红盘覆盖时看不见（回到"红盘实心盖蓝"的老问题），但**不会更糟**。
- 工作量：删除 `AirDiscQueue` 的裁剪分支（≈30 行），保留排序与队列。

### 方案 B（推荐先做）：裁剪只做"整盘判断"，不做逐行
- 规则简化：若小蓝盘与「更大蓝盘 ∩ 红盘」的**面积占比 > 阈值**（如 60%）→ 整盘不画（等于被吃掉）；
  否则整盘画（盖在红上）。
- 效果不是精确裁剪，但**绝不会出现残条/错位/消失**，且实现只有几行。
- 阈值可调（0% = 永不裁，100% = 只要沾边就不画）。

### 方案 C（精确但成本高）：把差集做成"纹理蒙版"
- 每帧在 CPU 上生成一张小尺寸蒙版（如 256×256）覆盖该盘，用 `Pixmap` 画椭圆差集，
  上传一次纹理后用 `TextureRegion` 贴到盘位置。
- 优点：精确、无矩形台阶、无批超限；缺点：每帧一次纹理上传（v79–v82 证明上传在本机**不可靠**，
  所以这条路要先用最小样例验证上传是否真的生效）。

### 方案 D：把"裁剪"交给地图本身
- 干脆不画"被覆盖"的盘，改为在**省份面板/悬浮提示**里显示"该省范围被更大范围覆盖"，
  地图上只画最大的那几个圈。最省性能，但信息量下降。
