## 三、实现（无一处手写 smali）

```
data/tno_opening_layout.json        版式唯一真源
tools/gen_tno_opening_assets.py     生成 6 张贴图（面板底图/页签/导航/海报）
tools/gen_tno_opening.py            生成两个新 smali 类 + 注入 MenuManager 钩子
tools/selftest_tno_opening.py       汇编前自检（标签/极性/引用/版式）
baseline/build_candidate.sh         换 dex + 注素材 + 对齐签名 + 三重自检
```

新增两个类（5,530 → 5,532）：

- `menusInGame/TNO_PanelImage` extends `Button`
  - 一张贴图 + 可选文字 + 点击回调；`mode` 0 装饰 / 1..4 切页 / 10·11 翻页 / 12 关闭
  - 重写 `draw()` 绕开 `Button.draw` 的"不可点→45% 透明"分支
- `menusInGame/TNO_OpeningScreen` extends `Menu`
  - 构造时算几何 → 建 15 个元素 → `initMenu(菜单矩形外扩 offX/offY)` 
  - `showPage(i)`：正文显隐 + 页签换图 + 功能页要点显隐
  - `doClose()`：先 `takeEventDecision` 给事件结案（避免读档重弹），再 `actionCloseMenu()`

挂载点：`MenuManager.rebuildInGame_Event()` 开头判 `event.id == "TNO_opening"`，
把 `IN_GAME_EVENT` 槽换成 `TNO_OpeningScreen`（与 `InGame_Event` 同一槽位、同一套
`setVisible + setOrderOfMenu` 流程）。事件侧只需 `popUp=true`（默认是 false！）。

## 四、踩过的坑（都写进了自检）

1. **元素坐标是相对 `menuPosX` 的**。`drawMenuElements` 里屏幕 X = `element.posX + menuPosX`，
   而 `initMenu` 会把 menuPosX 设成面板位置 —— 直接写绝对坐标会**偏两倍**。
   → 元素坐标必须写成 `面板内偏移 + 面板坐标`。
2. **分支极性**。`if-lt/if-ge`、`if-eq/if-ne` 写反不会汇编失败，只会"点了没反应"。
   首版连续写错 6 处（页签高亮、正文显隐、要点显隐、翻页回绕、关闭空判）。
   → `tools/selftest_tno_opening.py` 的 S2 项专门盯这批判断，已用变异测试验证能抓到。
3. **寄存器上限**。`move/iput/iget` 等 12x/22c 指令只能用 v0..v15；
   参数从 `registers - 参数个数` 起算。为塞下 `Button.init` 的 11 个参数，
   构造函数改成 `flags = (mode<<1)|clickable` 压成 6 个参数。
4. **`Event.popUp` 默认 false**，不显式写 `popUp=true` 就不会弹面板。
5. **贴图懒注册**。6 张图在 `TNO_OpeningScreen.<clinit>` 里 `ImageManager.addImage`，
   不用改 `InitGame.loadImages_1()`（960 个静态字段的坑绕开）。

## 八、v1.1 修复（装机实测暴露的两个问题）

### 1. 挂载钩子极性反了（面板一次都没出现，弹的是原生事件窗）

`if-nez v0, :tno_open_normal` 实际含义是"ID 命中(equals=1)就跳回原路径"，
正好把两种情况对调了。第一版装机后看到的就是 `InGame_Event` 原生事件面板
（标题「终序千禧开局 / 发生在唐山的事件」+ 四选项 + 912.png 四分格图）。

→ 改成 `if-eqz v0, :tno_open_normal`；
→ 自检新增 **S2e**：直接断言 `MenuManager` 里必须是 `if-eqz v0, :tno_open_normal`，
   且不得残留 `if-nez`、必须能构造 `TNO_OpeningScreen`。

> 教训：S2 之前只查了两个新类，**钩子本身没被检查**。凡是"注入到既有方法里的分支"，
> 也必须进自检，否则极性错误两次犯。

### 2. 贴图注册挪到启动期

`TNO_OpeningScreen.<clinit>` 里调 `ImageManager.addImage` 会在**事件回调线程**上创建
GL 纹理，时机赌运气。改为生成器把 6 张贴图注册注入 `InitGame.loadImages_1()`，
走的是 `Images.tnoFrame` 那套已验证路径（启动期、GL 上下文确定可用）。

### 3. 加了自检探针

面板构造成功会写 `nTNO build ok` 到
`/storage/emulated/0/Android/data/age.of.history3.qiamxi.zhiri/files/aircfg_diag.txt`，
装完起一局后 `adb-shell cat` 一下就知道面板到底建没建。

## 九、v1.2 流程复盘：为什么极性错误能连犯 7 次

### 根因不是"不小心"，是"手写控制流 + 假闸门"

| 部分 | 谁产出的 | 有极性风险 |
|---|---|---|
| 版式坐标 / 元素表 / 数组下标 | Python 按 JSON 算 | 无 |
| 图片 id / 字段名 / 方法签名 | Python 拼 | 无 |
| **控制流（if-*/goto 怎么连）** | **人写模板、Python 原样吐出** | **有** |

所谓"由生成器产出"只覆盖了数字，**控制流仍然是手写 smali**。这就是工作流第一条想禁止、
但被 f-string 伪装成合规的那部分。

三道闸门为什么全放过：
- 汇编器：`if-eqz` 和 `if-nez` 都是合法指令
- dex 指纹：分支反了结构一模一样
- 变更范围门禁：只数"变了几个方法"，不看变得对不对

第四道（S2 正则自检）是我自己写的，两个致命缺陷：
1. 它断言的是"我以为写对了的代码形状"，等于自己给自己判卷；
2. 检查范围按构造就漏掉**注入进既有文件的那段**（`MenuManager` 钩子）——第 7 次错正好落在这里。

### 结构性修法：改成"跑一遍"

新增 `tools/gate_behavior.py`：一个够用的微型 Dalvik 解释器（覆盖本项目生成代码用到的指令子集），
给定初值**执行**方法，记录 `invoke-*/new-instance/字段写入` 等副作用，再按用例断言行为。

```
B1 TNO_PanelImage.actionElement   mode=0/1..4/10/11/12/99 → 只能触发对应那一个动作（连参数一起查）
B2 TNO_OpeningScreen.prevPage/nextPage  首尾回绕
B3 TNO_OpeningScreen.showPage    第 i 页正文可见 + 页签换图 + 功能页要点
B4 MenuManager.rebuildInGame_Event  id 命中 → 槽里必须是 TNO_OpeningScreen；不命中 → InGame_Event
```

**变异测试（证明它真能抓到）**：

| 变异 | 结果 |
|---|---|
| 钩子 `if-eqz` → `if-nez`（就是这次漏网的那个错） | ❌ B4 4 项全红 |
| `showPage` 正文 `if-ne` → `if-eq` | ❌ B3 4 页全红 |
| 还原 | ✅ 全绿 |

它对**任意手写分支**都成立，不依赖事先猜到代码形状。以后凡是注入既有方法的钩子，
也必须进这个闸门。
