## 九、导弹管线实测补充（v2 追加）

### 9.1 两套时钟的实际入口

| 时钟 | 入口 | 触发方式 | 现状问题 |
|---|---|---|---|
| 真实毫秒（视觉） | `ProvinceDrawArmy.msFxStep`（9885）→ `msFxContact`（5592） | 每帧由绘制路径调用，开局/菜单打开时提前 return | **没有任何雷达圈判定** |
| 游戏小时（逻辑） | `AirMission.missileTick` | 无条件推进 | **和毫秒钟同时推进 = 双重计速** |

接触判定实测：

```smali
cmpl-float v9, v7, v8      # v7=本帧步进 v8=剩余距离
if-eqz v9, :msc
:msc
    invoke-static {p0}, AirMission;->msFxContact(...)
```

⇒ 只有"本帧步进刚好吃掉剩余距离"才接触，**雷达圈完全没参与**。

### 9.3 目标行为（用户口径）

- 导弹在**雷达圈内 且 屏幕内** → 走毫秒钟，接触结算（`msFxContact`）
- 导弹在**雷达圈外 或 屏幕外** → 走小时钟（`missileTick`），按游戏小时推进
- 两者**互斥**，不允许同时推进

实现要点：抽一个 `msInRadarAndOnScreen(mission)Z`，两处共用，避免逻辑漂移。

### 9.4 坐标系查证（结论：msFxX/msFxY 是**世界坐标**）

绘制端（`ProvinceDrawArmy` 4365–4390）把导弹画到屏幕上是这样算的：

```smali
v12 = mapCoords.getPosX()      # 相机
v13 = mapCoords.getPosY()
v11 = zoom

screenX = (msFxX + v12) * v11 - 7
screenY = (msFxY + v13) * v11 - 7
```

⇒ `msFxX/msFxY` **不包含相机与缩放**，是地图/世界坐标。

由此两条判定的正确写法：

| 判定 | 做法 | 用的量 |
|---|---|---|
| **雷达圈内** | `距离(msFxX/Y, 目标X/Y) <= radarRange` | 世界坐标距离，与 `AirForceManager:3201` 的雷达门同量纲 |
| **屏幕内** | `sx = (msFxX + mapPosX) * zoom`，`sy = (msFxY + mapPosY) * zoom`，判 `0<=sx<=GAME_WIDTH && 0<=sy<=GAME_HEIGHT` | 必须套相机+缩放，直接拿 msFxX 比屏幕宽高是错的 |

**坑**：不要用 `msFxX/msFxY` 直接和 `GAME_WIDTH/GAME_HEIGHT` 比 —— 会得出"导弹永远在屏幕内"（世界坐标数值通常远小于/大于屏幕像素），
于是 `missileTick` 永远不会被跳过，双重计速照旧。

### 9.6 雷达圈的真相（第二个量纲坑）

`AirForceManager` 3195–3203 的雷达门：

```smali
invoke-direct {v5, v4, v3}, AirForceManager;->provinceDistance(II)F
move-result v6                       # v6 = 省份距离
iget v7, p2, AirUnit;->radarRange:F  # p2 = 拦截机
cmpl-float v8, v6, v7
if-gtz v8, :cond_94                  # 省份距离 > radarRange → 跳过（打不到）
```

两个结论：

1. **雷达圈主体 = 拦截机（p2）**，不是目标。后续一律按此口径。
2. **`radarRange` 比的是「省份距离」，不是世界像素距离**。
   现配置 radarRange = 500~950，而 `provinceDistance` 实际只有 0~十几 →
   **这道门几乎恒真**，雷达圈在实战里等于没起作用。

⇒ 用户说的「导弹碰撞应在雷达圈内触发」，**不能直接复用 `radarRange`**：
   - 若沿用：圈外永远是假命题，改了也没效果；
   - 正确做法：给导弹单独一个量纲一致的阈值，例如
     `MissileRadarRange`（世界坐标距离）或「N 个省份内」，
     在配置里与 `RadarRange` 分开，互不干扰。

**这是必须先定的一件事**：导弹接触的"雷达圈"用**省份距离**还是**世界距离**？
- 省份距离：与现有 `provinceDistance` 一致、实现最简，但粒度粗（一个省几十像素）
- 世界距离：手感精确，但要在 `msFxStep` 里另算一份距离（该处已有 `v7/v8` 剩余距离，可直接复用）

我倾向**世界距离**（`msFxStep` 里现成的剩余距离就能用，零额外计算）。

## 十、导弹结算重构方案（性能前提下的更好结构）

### 10.1 原设计的意图（用户口径）

双时钟不是玩法，是**性能优化**：导弹在屏幕上飞时做逐帧高精度推进（好看、能看碰撞），
不在屏幕上时按游戏小时整段跳（省算力）。

### 10.2 原实现的三个缺陷

| 缺陷 | 后果 |
|---|---|
| 两条推进路径各自独立实现 | 逻辑会漂移（速度、到达判定各写一份） |
| 没有任何互斥标志 | 屏幕上飞的时候被两套时钟同时推进 → 跑得比设定快 |
| 接触条件里没有雷达圈 | 圈外也能结算；且屏幕外时"是否接触"完全依赖小时钟的整段跳 |

### 10.3 新结构：**一个推进函数 + 一个模式标志 + 与屏幕无关的接触判定**

```
advanceMode = visible ? MODE_FRAME : MODE_HOUR     // 每帧/每小时各算一次，O(1)
    visible = 在屏幕内 ?            // 世界坐标套 (pos+mapPos)*zoom 后判屏幕矩形
              （雷达圈不参与"是否需要被看见"）
advance(dt)   // 唯一推进函数，两条路径共用；dt 来源不同
    推进位置 → 判 contact：剩余距离 <= MissileRadarRange  →  结算
```

要点：

1. **接触判定只依赖距离（雷达圈），与屏幕无关**。
   屏幕外的导弹也必须能命中 —— 否则"离开视野就永远打不中"，任务无法结束。
   所以用户口径里的"屏幕内"只影响**推进粒度**，不该出现在接触条件里。
2. **一个 `advance(dt)`**：帧路径传 `dt=ms`，小时路径传 `dt=1小时`，内部逻辑完全一致，不会漂移。
3. **`advanceMode` 互斥**：`msFxStep` 只在 MODE_FRAME 时推进，`missileTick` 只在 MODE_HOUR 时推进
   → 双重计速从结构上不可能发生。
4. **雷达圈用世界距离**：`msFxStep` 里已有现成剩余距离，零额外计算；
   `radarRange`（省份距离，几乎恒真）保持原样不动，另加 `MissileRadarRange` 进机型配置。
5. 性能反而更好：`visible` 每帧只算一次坐标变换（本来绘制就要算），
   且不再有"两套逻辑都跑一遍"的浪费。

### 10.4 落地顺序

1. 机型配置加 `MissileRadarRange`（世界距离，独立于 RadarRange）
2. 生成器产出对应表列
3. 写 B8 四组合用例（屏内/屏外 × 圈内/圈外 → 谁推进、是否接触）
4. 抽 `advance` + `advanceMode`，改 `msFxStep`/`missileTick` 为调用方
5. 推进前把 `MS_SPD` 写成 `missileSpeed(modelAid)`
6. 跑闸门 → 出包（连机场归属一起）

## 十一、根治极性错误：Java → d8 → baksmali（已端到端验证）

### 11.1 验证结果（2026-10-19 实测）

```bash
javac --release 8 -d cls src/Demo.java                 # OK
java -cp /tmp/r8_8.3.37.jar com.android.tools.r8.D8 \
     --min-api 26 --output dex cls/Demo.class          # OK → classes.dex (672B)
java -cp "$(cat /tmp/smali_cp.txt)" org.jf.baksmali.Main \
     disassemble dex/classes.dex -o sm                 # OK
```

反汇编出来与自己写的 Java 语义**完全一致**：

```java
if (mode < 1) return 0;        →  if-ge p0, v0, :cond_5   (mode>=1 才继续)
if (mode <= 4) return mode-1;  →  if-gt p0, v1, :cond_a   (mode>4 才跳过)
```

⇒ 极性由编译器决定，**物理上不可能写反**。

### 11.2 工具链现状

| 组件 | 位置 | 状态 |
|---|---|---|
| javac | /usr/bin/javac | ✅ |
| d8 | `/tmp/r8_8.3.37.jar`（`com.android.tools.r8.D8`） | ✅ 已下载 |
| baksmali | /tmp/jars | ✅ 已有 |

### 11.3 还缺一块：游戏类的桩（javac 需要 classpath）

我们的 Java 要引用 `AirUnit` / `AirModelStats` / `CFG` 等游戏类，但这些只有 smali/dex，
javac 编译不过。解决办法：

```
tools/gen_java_stubs.py
   扫描 src/smali → 解析 .class/.super/.field/.method 签名
   → 生成同名空体 Java 源码（方法体 throw new RuntimeException("stub")）
   → javac 成 stubs.jar
然后：我们的 Java 用 -cp stubs.jar 编译 → d8 → baksmali → 落进 src/smali
```

### 11.4 迁移策略（不要一把梭）

| 类别 | 用什么写 | 理由 |
|---|---|---|
| **逻辑类**（有分支/循环的新代码） | **Java** | 消灭极性错误 |
| 数据表（`fill-array-data` 内联常量） | 保持生成器出 smali | Java 表达不了数组字面量的 dex 内联 |
| 对既有方法的注入（钩子） | 保持生成器 + 行为闸门 | 注入体太小，Java 化收益低、改造成本高 |

先迁一类做样板：`TNO_OpeningScreen` + `TNO_PanelImage`（已经写完、已有 B1–B5 用例），
用 Java 重写后对比反汇编与行为，确认闸门仍全绿，再决定是否迁 `AirMissileGate` 等。

### 11.5 成本

- 构建时间 +20~30s（javac + d8 + baksmali）
- 需要维护桩生成器（一次性）
- `baksmali` 产物的注释/行号与原手写不同，但**变更范围门禁比的是反汇编结果**，不受影响
- 行为闸门继续有效（它跑的是最终 smali），等于双保险

### 11.6 结论

**推荐迁移**。这一轮 8 次极性错误全部靠闸门事后拦截；
迁到 Java 后这一整类错误从"需要被发现"变成"不可能发生"，
闸门的作用回到它该做的"验证业务逻辑对不对"。

### 11.7 桩生成器 + Java 样板：端到端已跑通（2026-10-19）

新增 `tools/gen_java_stubs.py`：扫 smali 树，按需生成游戏类**空体桩**并编译。

三个必须记的点（都是踩出来的）：

1. **`javac` 必须带 `-encoding UTF-8`** —— 源码里有中文注释，默认 US-ASCII 会直接报
   "unmappable character"。
2. **桩源码必须写 `package` 声明**，否则编译到默认包，`-cp` 解析不到
   （表现为 `package aoc...does not exist`）。
3. **树外的库类型（libgdx 等）统一退化成 `Object`** —— 桩只要能编译过；
   否则每个字段都要连带生成 libgdx 的桩，没必要。

实测链路：

```
gen_java_stubs.py --classes aoc.kingdoms.lukasz.jakowski.CFG   → 桩编译通过
javac -cp 桩 AirMissileGate.java                                → OK
d8 --min-api 26                                                 → classes.dex
baksmali                                                        → smali
```

Java 版 `if (sx < 0f) return false;` 被编成 `if-gez p3, :cond_b` ——

## 十六、v1.5 闪退：VerifyError（已修，v1.7）

真机 logcat：

```

  stampAirUnit(AirUnit, AirUnit$AirType, int) failed to verify:
  [0x17] instance field access on object that has non-reference type Float
```

**根因：`p` 寄存器是 `v` 寄存器的别名，`.registers` 少写 1 就会重合。**

| 方法 | 窗口 | 后果 |
|---|---|---|

| `AirModelStats.applyModel` | `.registers 6` ⇒ `p0 == v5` | 方法体用 v5 做 `mul-float` 暂存，同样把对象寄存器写成 float |

两处都只差 1 个寄存器窗口，但**汇编器不校验、d8 不跑 ART 校验器**，能一路打包签名成功。
`applyModel` 的那处如果单独触发，`AirModelStats` 整类被丢，所有机型数值会静默失效。

修复：`applyModel .registers 6→7`（改生成器，防重生成回退）、`stampAirUnit 5→6`。

## 二十二、v23：编制跟着机型走（造出来的飞机不再是占位战斗机）

### 30.5 调研：科技树为什么"上下拖不动"（结论：没有禁滑开关，是算术阈值）

设备实测（日志 `nTTD rectX/rectY/rectW/rectH`）= `0, 60, 2680, 1200` ⇒
`GAME_HEIGHT=1260`、`iHeight = GAME_HEIGHT − titleHeight = 1200`。

- 节点 `posY = TreeRow×(iTechHeight+15) + 98`，`iTechHeight=120` ⇒ 行距 **135**；节点高 120。
- 画布 `Empty` 高 = `max(内容底+PADDING, iHeight)`（`<init>` 里 Math.max）。
- `Menu.updateScrollable()`：`iMaxSliderPositionY = max(posY+height)`，
  `scrollableY = iMaxSliderPositionY > iHeight`（**严格大于**）。

⇒ **只有"整棵树比一整屏还高"才允许纵向拖**。`scrollableY=false` 时四处各自丢掉 Y：

1. `MenuManager.actionDown`：`scrollableY||scrollableX` 才进拖动模式（X 为 true 所以进得去）；
2. `MenuManager.actionMove_MenuInnerElements`：`if (!getScrollableY())` 整段跳过 Y（位移公式本身没错）；
3. `Menu.updateMenuPosY`：`scrollableY=false` 时把目标值写回当前 `getPosY()` 再 return；
4. `MenuManager.update`：只有可滚才调 `Menu.update()`（甩动同步）。

X 能动是因为 r6d309 给科技树插了**专用增量分支**（`MenuManager:2580-2643`，绕开原生
`iSliderMenuStartPosX` 锚定），Y 没有对应分支。科技树自己从不写 `scrollableY`
（`relayoutDone` 只 `setMenuPosX`、`relayoutNodes` 只改 posX）。

**与 v32 的关系**：
- v31 数据 air 行是 `组*4+类型`（0..15）→ 内容底 2243 ⇒ `iMax=2248 > 1200` ⇒ **Y 确实能拖**，
  所以四国 16 行都能滚到，才看得见"别国节点"。
- v32 把行压成 `类型轴`（0..3）→ 内容底 623、`Empty` 取 1200 ⇒ `iMax == iHeight` ⇒ Y 不可拖，
  但 **4 行本来就在一屏里**，不需要拖。

需要"任何时候都能上下平移"的话，最小改法只有一行：`<init>` 里 `Math.max` 之后
`add-int v3, v3, v10`（画布高 = max(内容,面板)+面板 ⇒ iMax=2400 ⇒ scrollableY=true，
范围 = 1200 由 `updateMenuPosY` 钳制）。副作用：内容不满屏时也能拖出空白。
**不要**硬写 `scrollableY=true`：iMax 不变 ⇒ 范围 0，且 `scWatch` 三连发
`applyTopFilter→relayoutDone→updateScrollable` 会把任何手改覆盖回去。

另：`updateScrollable` **完全不看可见性**，而 `relayoutNodes` 过滤别国节点时只挪 posX=-2000
⇒ X 范围随页签收缩，Y 范围恒按全树算（切页签不会让 Y 更容易滚）。

## 三十二、v34：科技真的解锁机型 + F-35 点不了

### 32.1 "点了科技还是只能造三代机"

`AirModelPick.best()` 用的是一根**全局常量** `AIR_GEN_MAX = 3`，从来没人写它
⇒ 不管研究了哪一代，选型永远停在 gen<=3。空军科技线是展示品。

改法：`best(civID, group, type)` 从六代往下找"**该槽位的科技已经研究过**"的机型：

```

gen==3            → 直接返回（开局由 AirTechGrant 授予）
civ.getTechResearched(tech) → 返回该 aid
都没有            → 三代兜底
```
`AIR_GEN_MAX` 改成 **6**（只剩"保险丝"语义，不再参与判定）。

### 32.2 F-35 点不了（跨国共用的前置死锁）

F-35 是唯一跨国共用机型：EU 三个槽位 + US 两个槽位。而生成器给它的前置取的是
"首个槽位所属国家的上一代同类科技" = **112（A10，只属美国组）**
⇒ 欧洲玩家永远研究不了 112 ⇒ F-35 永久不可达（截图里那块黑的就是它）。

改法：`gen_air_techs.py` 对**跨国共用机型不挂前置**（`req = -1`）。
挂哪一条都会锁死另一国，这是两条不同的国别科技，`RequiredTech` 只能填一个。

### 32.3 闸门 B18

① `best()` 必须用 `AirTechCiv.aidTechOf` + `getTechResearched`，不许读 `AIR_GEN_MAX`；
② `AIR_GEN_MAX` 的 `<clinit>` 常量必须是 6；
③ `AID_TECH[64]` 与科技表槽位逐条对账（64 槽全覆盖，从 `data/air_tech.json` 独立算）；

### 32.4 未做（下一批：总节点与沿用加成）

用户要的"总节点（欧洲四代/五代/六代空军）+ 沿用飞机加成"**没有做**，原因是调研出数值冲突：

- 设计稿（`data/air_tech.json` 的 `carryOver`/`genBase`）写的是
  `hp *= genBase[G].hp / genBase[f].hp`，其中 f = 机型**首次出现的代**、G = 它被沿用到的代。
  按 `genBase`（3:30 / 4:100 / 5:600 / 6:1500）算，四代沿用件在六代槽位要乘 15 倍。
- 但现在 `AirModelStats` 的数值表是**按 aid（槽位）**生成的：同一个 J11，
  aid0（三代槽）= 25、aid18（四代槽）= 142 —— 沿用件**已经自动按槽位代际抬过了**。
  再乘一次 genBase 比例会直接把数值打爆（142 × 15 ≈ 2100）。

所以要么改数值表让沿用槽位保留"机型原代"数值、再用总节点抬上去；要么把总节点改成
"补齐到该代基准"的小幅修正（现在沿用件已到该代约 95%）。这两条是不同玩法，需要用户定。

## 三十四、v36：空军科技名被编制名覆盖（用户实测）+ H29/B3 漏改名

### 34.1 真因：`buildTechnologiesNames()` 拿编制名覆盖科技名

`TechnologyTree.buildTechnologiesNames()`（smali 里 `:cond_7a` 那段）逻辑是：
**只要某科技解锁了单位，就把 `Technology.Name` 改成该单位行的 `Data_Army.Name`**。
v35 让三代编制也挂上了科技（`RequiredTechID` 全部 >= 0），于是空军 53 条科技全都有单位，
科技节点名字就被编制名（`J11战斗机`）盖掉了 —— 用户看到的就是"科技名不是裸型号"。

修法（一行钩子）：
```
invoke-static {v0}, AirTechCiv;->isAir(I)Z   # v0 = techID
move-result  v1
if-nez       v1, :cond_c3                    # 空军科技直接跳过改名
```
`AirTechCiv.isAir(int)` = `maskOf(techID) != 0`，由 `tools/gen_air_tech_civ.py` 生成。

### 36.2 科技 ID 固定化（本批重点，`data/air_tech_ids.json`）

**病根**：旧实现 `id = BASE_ID + 该机型"首次出现 aid"的排名`。增删/移动一格机型，
后面所有 ID 整体平移 ⇒ 旧存档里"已研究"的号指到别的机型（v37 台账 35.10 第 7 条）。

**做法**：新增 `tools/air_tech_ids.py` + 真源 `data/air_tech_ids.json`：

```
baseID   99     空军科技起始 ID（= AirTechCiv.AIR_BASE）
nextID   153    水位线：下一个可用 ID；删到末尾也不回退（不重用已发出去的号）
ids      {机型: techID}    当前机型 → 固定 ID；已有的一律沿用
aliases  {旧名: 新名}      改名登记：新名继承旧名的 ID（旧存档仍解锁同一机型）
retired  {机型: techID}    已删机型：ID 留空（占位节点），不复用、不重排
```

分配顺序：① 改名继承 → ② 复活（机型又回来了就取回原号）→ ③ 新机型 `nextID++`
→ ④ 退役（新机型表里没有的 code 移进 retired，ID 由占位节点保住）。
**性质：任何一次增删，其余机型的 ID 一个不动**（B22③④ 用临时副本实测）。
`gen_air_techs.py --init` 可按当前机型表重新冻结（有表时拒绝覆盖，防手滑）。

**占位节点（为什么必须有）**：`TechnologyTree.loadTechnology()` 是按 JSON **文件顺序**
逐个 `add()` 进 `lTechnology`，之后全程 `get(ID)`。所以不只是"ID 连续"，**文件顺序也必须
等于 ID 升序**；ID 有洞 ⇒ 后面的科技全体错位（比存档平移更糟）。删机型时在它的 ID 上发一个
`Category: "air"` 的空节点：`MASK=0` ⇒ 任何国家组的 `allowedGroup` 都是 false（不可研究、
不给高亮），但它占住下标，后面的 ID 不会动。
本批没有删机型 ⇒ `retired = {}` ⇒ 仍 54 个节点（99..152）。

**连续性断言适配**：`gen_air_tech_civ.render()` 的断言从"id == base+序号"改成
"id == base+序号 **且** base == `air_tech_ids.json.baseID`"，并要求占位节点 mask 可以等于 0
（以前 `mask_of_node` 见到 0 直接 `SystemExit`）。`AIR_BASE` 仍 99 —— 本批 ID 与 v37
**逐位相同**，`AirTechCiv.<clinit>` 在变更范围闸门里**根本没出现**（数组一个字节没变），
这是"ID 没动"最硬的证据。

**生成器链新增一步**：`gen_air_techs` 之后要跑 `gen_air_tech_civ.py`
（AirTechCiv.java 是它的产物；v37 的清单里漏写了这一步，本次补上）。

### 39.3 交付二：`tools/fmo.py`（编排器，四个子命令）

```bash
python3 tools/fmo.py preflight --template <apk> [--stage <dir>] [--ensure-stage]
python3 tools/fmo.py verify    --apk <apk> [--dex <dex>]
python3 tools/fmo.py build     --template <apk> --dex <dex> --stage <dir> --out <apk>
python3 tools/fmo.py gate      [--batch <name>]
```

**preflight 检查项**（任一失败退出码 1）：模板 APK 存在 / 可读 / 非空（并打印 md5 与
package+versionName，防用错模板）→ `/sdcard` 与 `/tmp` 剩余 ≥ 5G（满盘会被误报成"装机失败/
会话异常"）→ `/tmp/smali_cp.txt`、`/tmp/r8_8.3.37.jar`、`/tmp/debug.keystore` 就位 → `--stage`
目录存在且非空（空则报 v39 的 `zip error: Nothing to do` 坑，并提示 `--ensure-stage`）。

**verify 六项**：包内 `classes.dex` md5 与 `--dex` 对比 → `aapt dump badging` 成功 →
`apksigner verify` 成功 → `dex_fingerprint.py` 输出类/方法/字段 + 两个指纹 → `zipalign -c 4` →
`AndroidManifest.xml` md5 打印。任一失败退出码 1。

**build**：preflight → `baseline/build_candidate.sh` → verify → 写
`baseline/batches/<out 文件名去扩展>.json`（时间戳、git HEAD + dirty、模板 path/md5/size/
package/versionName、stage 文件数与字节数、dex md5、APK size/md5、包内 dex md5、manifest md5、
verify 结论）。`build_candidate.sh` 失败不写台账、不留半成品。

**gate**：依次跑 `gate_behavior.py` → `lint_verifier.py` → `gate_java_first.py --include-worktree`
→ `selftest.sh`，逐步打通过/失败与耗时，失败时打**最后 20 行**输出，汇总后退出码取最差。
`--batch <name>` 只是标签；若 `baseline/batches/<name>.json` 存在，会打印该批的模板/产物 md5 做对照。

### 39.4 两个坑的固化方式（细节）

1. **空素材目录 → `zip error: Nothing to do`**：preflight 数 `--stage` 下文件数，0 就红，文案直接
   引用 v39 的报错原文。`--ensure-stage` 不"凭空造" `numOfImages.txt`（数字不对会让图标错位），
   而是从**模板 APK 里按原路径抽出原始字节**（`zipfile` 读 `assets/game/units/unitsImages/numOfImages.txt`），
   保证"未改"；模板里没有这个条目时明确拒绝，要求人工放本批素材。
2. **必须前台打包**：`fmo.py build` 不做任何 `&`/`nohup`/`setsid`，直接 `subprocess.run`
   等 `build_candidate.sh` 返回；脚本失败就打印最后 20 行并不写台账（"失败不沿用旧产物"）。

另外两条（模板显式、指纹判据）也写进了命令本身：`--template` 必填且 preflight 打 md5；
verify 一定跑结构指纹，不再拿 md5 当等价判据。

## 三十八、v40：飞机雷达盘重叠不再变亮（离屏 FrameBuffer 一次合成）

- 病根（v39）：`RadarDisc.draw` 每个任务画一次盘、每次 `setColor(1,1,1,0.2)` 各混一次
  ⇒ 屏上 = `(1-0.8^N)·盘 + 0.8^N·底`，任务一多就一片白；建筑盘是"所有省份的盘烘进同一张地图纹理、
  最后整图画一次 α=0.2" ⇒ 重叠天然不变亮。本批把飞机盘改成后者的做法。
- 新类 `map/province/RadarOverlay`（手写 smali，原因同 RadarDisc：`gen_java_stubs.py` 把 libgdx
  退化成 `Object`，`fb.begin()` / `glClearColor(...)` 在 javac 阶段不成立；已登记
  `baseline/smali_exceptions.txt`）：
  - `ensure()`：按屏幕尺寸懒建 `new FrameBuffer(RGBA8888, w, h, false)` + `TextureRegion`
    （`flip(false,true)` 把 FBO 上下颠倒的 v 翻回来），尺寸变了先 `dispose()` 再重建；
    全程 try/catch，失败把 `fb`/`fbRegion` 置 null 后直接 return；
  - `begin(sb)`：`sb.end()` → `fb.begin()` → `glClearColor(0,0,0,0)` + `glClear(GL_COLOR_BUFFER_BIT)` →
    `sb.begin()` → `setColor(1,1,1,1)` → `active=true`；`fb`/`fbRegion`/单位盘 region 三件套缺一不激活；
    上一帧漏了 `end()`（active 残留）时先自愈调 `end()`，避免 FBO 一直绑着把整块画面画进离屏；
  - `drawDisc(sb,cx,cy,rx,ry)`：**FBO 内 alpha=1.0**（后画覆盖先画 ⇒ 重叠像素饱和成同一个值，不累加），

    `active=false`（FBO 不可用）时**回退 `RadarDisc->draw`**，雷达圈不会消失；
  - `end(sb)`：`sb.end()` → `fb.end()` → `sb.begin()` → `setColor(1,1,1,0.2)` → `fbRegion` 铺满
