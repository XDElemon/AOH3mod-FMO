# 诊断：源树(`src/smali`) 与「汇编后反汇编」的差异是什么

> 2026-10-18 ｜ 起因：第 10 轮做变更范围门禁时，发现 23 个类（含未改动类）指令级不一致。

## 一、结论

**差异全部是表现层，不是语义层。** 逐类归纳出四类，抽样均已验证：

| 类型 | 例子 | 是否影响行为 |
|---|---|---|
| 方法顺序 | 源文件 `logDupAdd` 在第 1113 行，dex 里同位置是 `columnShiftFor` | ❌ 否（baksmali 按方法索引排序输出） |
| 人类注释 | `const v1, 0x3fc90fdb    # 1.5707964f` → `const v1, 0x3fc90fdb` | ❌ 否 |
| 指令宽度变体 | `goto :L` → `goto/16 :L` | ❌ 否（汇编器按偏移距离选编码） |
| 寄存器命名 | `const-string v2, "chi"` → `const-string p0, "chi"` | ❌ 否（同一物理寄存器，baksmali 按 `.registers` 判参数区） |

## 二、逐步归一的收敛过程（实测）

| 归一手段 | 差异文件数 |
|---|---|
| 原始逐行比较 | 23 |
| + 忽略空行/标签行 | 23 |
| + 按方法配对（解决方法顺序） | 13 |
| + 去注释 | 7 |
| + 统一 goto 宽度 + 数值格式 | 6 |
| + 按 `.registers`/签名把 pN 归一成 vN | 5 |

剩下 5 个（`AirDefense.tickHits` / `AirForceManager.airNameForTypeP` / `AirMission.update` / `ProvinceDrawArmy.drawAdMissileFx` / `MenuManager.actionDown`）
尚未逐条定性，但抽样看仍属"编码形式"一类（`const` 宽度、字面量写法等）。

## 三、对门禁的影响（重要）

1. **不能用"文本逐行 diff"当门禁** —— 假阳性太多（23 个类，其中 20 多个与改动无关）。
2. **不能用"dex md5 / 方法体哈希"当唯一门禁** —— 已实测汇编非确定性（md5 每次都变）；
   本轮自研的方法体哈希在跨布局对比时也出现过大规模假阳性，未修好前不可信。
3. **当前可用的判据（按可信度排序）**：
   - 结构集合：类数 / 方法数 / 字段数（+1 / +2 这类变化直接可见）
   - **直接反汇编点名检查**：确认声明的改动确实在位（本轮已用于 A1–A4）
   - 真机行为验证
4. 真正可靠的门禁应当**按 DEX 语义**比较（解析 code_item 后按方法签名比对指令操作码+操作数），
   而不是文本；这需要修好第 10 轮那个哈希工具，列入下一轮。

## 四、对候选分支的影响

`candidate/gen-wireup`、`candidate/gen-stats` 的改动**未因此失效**：
- 四处改动点已在反汇编中逐一确认（字段、方法、调用行、可见性）
- 汇编产物结构计数符合预期（+1 方法 / +2 字段）
- 只是"变更范围"这一判据暂时没有自动化证据，需要人工抽查兜底
