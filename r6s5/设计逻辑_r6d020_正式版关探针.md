## 1. 版本号 + 一句话定位
**r6d020 = 对外正式版**：功能与 r6d018 完全一致，但**所有调试探针默认彻底静默**（不写日志文件、不打 logcat）。

## 2. 设计目标
- 玩家可见的问题：诊断版每次进游戏都会往 `files/airdbg_key.txt` 写日志（实测一局 8~10 MB），既占空间又拖性能；logcat 也被刷屏。
- 上层意图：**同一套代码，两种形态** —— 调试（配置 `debug:1`）与对外（默认 `0`）。对玩家零可见副作用。

## 3. 设计规则与判定顺序（人话）
```
任何探针被调用 → 进入 AirDbgLog 的入口方法之一：
  ① dKey(tag,msg)        ← 主漏斗（绝大多数探针）
  ② d(tag,msg)           ← 旁路（发现 nDE_ENTER 就是从这里漏的）
  ③ logOnce(tag,msg)     ← 旁路（去重型）
  三者在方法开头**统一先判总闸**：
      若 dbgOn == false  → 直接 return 0（什么都不做、不拼串、不写盘）
      否则               → 照常 Log.d（logcat）＋ StringBuilder 累积 ＋每 500ms 落盘一次
dbgOn 的来源（每回合刷新）：配置文件 debug 键 → dgDebug → dbgOn
  且 dgDebug 的编译期默认值 = 0（<clinit>）⇒ 配置文件缺失也静默。
```

## 4. 参数与阈值表
| 名称 | 当前值 | 含义 | 改动影响 |
|---|---|---|---|
| `debug`（配置键） | **0** | 探针总闸 | 1 ⇒ 恢复写 `airdbg_key.txt` 与 logcat（调试用） |
| `dgDebug`（默认值） | 0 | 无配置文件的兜底 | 改 1 ⇒ 默认就开探针（对外版禁止） |
| `dbgOn`（运行时） | false | 三个入口读的开关 | 每回合由 `demoLoadCfg` 刷新 |
| 落盘节流 | 500 ms | `dKey` 内刷新间隔 | 与本次无关（开关关闭时不执行） |
| `activeMissions` 实现 | `java.util.ArrayList` | 任务列表 | 原为 `DebugMissionList`（每次增删 `Log.d`+`getStackTraceString`） |

## 5. 状态与生命周期
- `dbgOn`：静态布尔，进程内有效，每回合由配置刷新；**不进存档**。
- 探针调用点：**全部保留**（不删代码，只关闸）⇒ 需要排查时改一个 `debug:1` 就能恢复全部观测能力。
- 本版**不涉及**任何飞机/机场/AI 实体逻辑。

## 6. 边界与不变量
- 不变量①：**所有**对 `android.util.Log` 的调用必须在 `AirDbgLog` 内（门禁 77-4，全树扫描）。
- 不变量②：三个入口（`dKey`/`d`/`logOnce`）**都必须**有 `dbgOn` 闸（门禁 77-1、78-1）。
- 不变量③：闸的极性必须是 `if-eqz`（**关着就跳走**）——写反会导致"只有开调试才静默"（门禁 77-1/78-1 会在装机前拦下）。
- 不变量④：静默出口必须在方法体内、标签独占一行、其后紧跟 `return`（门禁 78-2/78-3）。
- 明确不改：AI 空军业务逻辑、判定方向、配置项语义、水印、启动弹窗、`AA_Game`/`initialize`。

## 7. 玩家可感知的表现
- 正常：进游戏无任何日志写入；logcat 干净；**玩法与 r6d018 完全一样**（水印、启动弹窗、自动打击/巡逻、AI 混编造机都在）。
- 异常（bug）：`files/airdbg_key.txt` 持续增长 ⇒ 说明还有第四个旁路入口没接闸（排查方法：`logcat | grep AIRDBG` 看是谁）。

## 8. 失败与回退
- **不是故障**的静默：`debug:0` ⇒ 本来就不该有输出。
- 需要恢复观测：把 `files/strike_config.json` 的 `debug` 改 1，进游戏即恢复（无需重装）。
- 崩溃类 bug：`VerifyError` ⇒ 回滚 `.pre_r6d020` / `.pre_r6d019` 重汇编重建。

## 10. 变更清单摘要
1. `AirDbgLog.dKey`：顶部**恢复** `dbgOn` 总闸（`if-eqz` ⇒ 关着直接返回 0）。
2. `AirDbgLog.d(String,String)I`、`AirDbgLog.logOnce(String,String)I`：**新增**同款总闸 + 静默出口标签（r6d020，补旁路）。
3. `AirForceManager`：`activeMissions` 初始化 `DebugMissionList` → `java.util.ArrayList`（去掉每次增删 logcat + 堆栈字符串的开销）。
   > ⚠️ **本条已被 r6d021 判为错误改动并订正**：`DebugMissionList extends java.util.concurrent.CopyOnWriteArrayList`，它提供的是**线程安全迭代**（渲染线程迭代 / 回合线程增删），日志只是附带。换成 `ArrayList` 会导致 `ConcurrentModificationException` 闪退（已发生）。r6d021 已改为直接使用 `java.util.concurrent.CopyOnWriteArrayList`（保留线程安全、去掉日志）。**教训：动类之前必须看 `.super`。**
4. 删除已无引用的类文件 `DebugMissionList.smali`（5519 → 5519-1 个 smali）。
5. 设备配置 `files/strike_config.json` 的 `debug` 写回 **0**。
6. 新增门禁 **77**（5 条 + 4 负样本）、**78**（4 条 + 3 负样本）。

## 附：本批的"探针旁路"发现（血案记录）
- 现象：恢复 `dKey` 总闸后，日志文件已是 0 字节，但 logcat **仍在刷** `AIRDBG: nDE_ENTER`。
- 原因：`AirDbgLog` 里还有两个**独立入口** `d(...)I` 与 `logOnce(...)I` 直接调 `Log.d`，不经过 `dKey`。
- 教训：**"漏斗唯一"必须靠门禁证明，不能靠假设**——门禁 77-4 只查了"Log 调用点在 AirDbgLog 内"，没查"是否都过闸"；所以补了门禁 78-1（三入口都必须有闸）。
