# 调研 · r6d050 第二轮：状态机缺口定位（为什么"治本"不是定时器）

> 结论：停滞**不是"时间不够"，而是状态机缺了三个"结构性转移"**；正确的治本是**补齐转移（用"师的实际位置"作判据）**，而不是定时/强制推进。

## 1. 状态机全貌（`AirMission.update()`，751 指令，`packed-switch` 按 state.ordinal）

| ordinal | state | 分派块 | 做什么（逐字要点） |
|---|---|---|---|
| 0 | PLANNING | `pswitch_98` | 检查就绪 → 设所有 `assignedAircraft.isInFlight=true` → **`state=EN_ROUTE`** → `pickupAirDivision()` → `calculateDistance()` → 重置动画时钟 → `return-void`（**`um_p0end:`** 日志） |
| 1 | EN_ROUTE | `pswitch_ff` | `roundsInFlight++`；**若 `roundsInFlight >= distanceToTarget` → `:cond_131`（到达路径）**；否则查 `allAircraftLost()`（真→ABORTED+回家） |
| — | （到达路径） | `:cond_16d` | `placeAirDivision(target)` + **`state=EXECUTING`**（`um_sw:st=2`） |
| 2 | EXECUTING | `pswitch_19f` | `executeAttack()`、`a1bReHunt()`、`lingerRounds++`；（另在 `:cond_131` 附近无条件判断 `shouldReturn()` → 切 RETURNING） |
| 3 | RETURNING | `pswitch_28a` | `roundsInFlight++` → `tryHunt()` → **若 `roundsInFlight >= distanceToTarget`** 才做"到家判定"：`flightProgress≥0.98 || animElapsedMs≥30000` → `state=COMPLETED` + `returnAirDivisionHome()` + `returnToBase()` |
| 4/5 | COMPLETED / ABORTED | — | 终态 |

推进器：`moveDivisionAlongFlight()`（576 指令）
```
① 若 airhqDivision == null ⇒ return-void（★ 师没了就永远不动）② airDivSegAnimMs += 0x10③ 按 sourceProvinceID→targetProvinceID 的屏幕坐标插值算当前点 → Game.setProvinceID_Point(x,y)④ 若新省 != airDivisionAtProvinceID ⇒ 换段（更新 prev/at + 新段时长）
```
返航段建立：`setupReturnLeg()`（`sourceProvinceID = airport.provinceID`；`targetProvinceID = airDivisionAtProvinceID`；`distanceToTarget = calculateDistance()`）

## 2. 三个缺口（→ 三类停滞，一一对应）

| 缺口 | 现象（与抓样一致） | 为什么"定时器"不是治本 |
|---|---|---|
| **G1 起飞没有"失败出口"**：PLANNING 的就绪门若永久不成立（或 `pickupAirDivision()` 拿不到师），既**不重试**也**不作废** | 4 个僵尸任务：`s=0 at=-1 ahq=0`，长期占用"在航"配额 | 超时作废只是"事后擦"，真正该补的是"拿不到师 ⇒ 明确放弃并释放资源" |
| **G2 到达判据用的是"计数器收敛"而非"师的位置"**：EN_ROUTE 的到达需要 `roundsInFlight >= distanceToTarget`；而 `roundsInFlight` 在进入 EN_ROUTE/RETURNING 时被**清零**，`distanceToTarget` 由 `calculateDistance()`（像素级）给出 ⇒ 两者的量纲/生命周期不同 ⇒ **可能永远不收敛** | 8 个 `s=3 at==tg`：师明明已在目标省/家，却卡在返航态 | 强制推进会把"师的位置/任务记录"再次搞脱节；正确做法是**用"师实际所在省"判定到达/到家** |
| **G3 缺"到家"转移**：RETURNING 没有"`师已在机场省` ⇒ 立即结算"的规则（只有 G2 那个计数器路径） | 同上 8 个；且 `s=1/2` 的飞机被永久钉在地图上（图标"流窜"的观感来源） | 同 G2 |

另：`moveDivisionAlongFlight` 的 ① 表明——**只要 `airhqDivision==null`，该任务在任何态都不会再动**，这正是"僵尸/幽灵"的物理来源。

## 3. 治本方案（结构性，不引入任何定时器）

新增 **`AirMission.tickInvars()V`**（同类的**新方法**，因此可以直接调 `pickupAirDivision/placeAirDivision/returnAirDivisionHome/returnToBase` 等 private 方法），并在 `update()` 入口加 **1 条 `invoke-static`**（单点、零寄存器风险）。规则：

```
R1 若 airhqDivision == null:
     · PLANNING      ⇒ 再试一次 pickupAirDivision()；若 assignedAircraft 为空/全灭 ⇒ state=ABORTED + 释放（结构性放弃）
     · EN_ROUTE/EXECUTING/RETURNING ⇒ state=ABORTED + returnAirDivisionHome()（清理残账）
R2 若 state==EN_ROUTE 且 airDivisionAtProvinceID == targetProvinceID
     ⇒ placeAirDivision(target) + state=EXECUTING        # 到达＝“师真的到了目标省”
R3 若 state==RETURNING 且 (airDivisionAtProvinceID == sourceAirport.provinceID 或 distanceToTarget<=0)
     ⇒ state=COMPLETED + returnAirDivisionHome() + returnToBase()   # 到家＝“师真的回了机场省”
R4 （保留既有）roundsInFlight>=distanceToTarget 路径照旧，作为次级条件，不删
```
要点：**把"到达/到家"的判据从"计数器收敛"改为"师的实际位置"** —— 这与 `moveDivisionAlongFlight` 更新 `airDivisionAtProvinceID` 的事实一致（它是唯一权威位置来源），因此不会产生新的脱节。

## 4. 与"定时器方案"的对比

| 维度 | 定时器/强制推进 | **结构性补转移（本方案）** |
|---|---|---|
| 依据 | 时间（与游戏逻辑无关） | **状态一致性不变量**（师的位置 / 资源存在性） |
| 副作用 | 可能把任务推到错误省、制造新的脱节 | 只会把任务推进到它**本来就应该在**的状态 |
| 覆盖 | 只覆盖"卡住且超时" | 覆盖 3 类缺口（僵尸、在航不推进、返航不结算） |
| 可验证 | 难（凭观感） | 易：给 R1/R2/R3 各加计数器（`ivAbort/ivArrive/ivHome`），抓样即证 |
