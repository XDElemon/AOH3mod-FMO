# 调研 · r6d061 第三轮（定稿）：配置加载"自证 + 修正"施工方案

> 基线：**装机 dex 反汇编**（`/tmp/inst_out` → 复制为 `/tmp/w3a/smali`，5519 个类）。
> 理由：`/tmp/revx` 与装机 dex 不一致（2668 行差异，`<clinit>` 指令序不同），`/tmp/w3a/smali` 原树已丢失 ⇒ 只能以"正在运行的产物"为真值。
> 目标：不再依赖任何既有推断，**让应用自己把"读到什么 / 解析出什么 / 字段里是什么"写进诊断文件**，同时顺手把字段按配置重写（=修复）。

## 2. 设计规则与判定顺序（人话）

1. 进程启动 → `AndroidLauncher:24 demoLoadCfg()`（旧链路照旧执行）→ 末尾插入的 `cfgFix()`。
2. `boot()`（第 26 行）→ 先把 `dbgOn=1` → **再调 `cfgFix()`** → 然后才打印 `BOOT2`。
   ⇒ **BOOT2 从此反映"cfgFix 修正之后"的字段值**，与 `CFGT3` 可以互相校验。
3. `cfgFix()` 内部顺序（固定，不可换）：
   ① 用写死的绝对路径调 `cfgReadText` 读文本（`java.io`，失败返回 null）；
   ② 打 **CFGT** 自证行：`tlen=<text 长度，null 记 -1>` + `s=prob,pin,debug,ai_cap,ai_build`（用**哨兵默认 -7** 解析 ⇒ 值为 `-7` 表示"该键在文本里找不到"，为真实数字表示"找到并解析成功"）；
   ③ **写回 12 个字段**（语义与旧链路一致；`prob` 钳 [0,100]；`debug` 同时决定 `dbgOn`）；
   ④ 打 **CFGT3** 自证行：重新 `sget` 字段 ⇒ 证明 `sput` 生效。
4. 若 `text==null`：CFGT 打 `tlen=-1`，所有键判为"缺失"⇒ 写回默认值（与旧链路一致），不再继续诊断。

**判定顺序的优先级**：`cfgFix` 的写回位于旧解析块之后（A2）且在 `BOOT2` 之前（A3）⇒ **cfgFix 是最终仲裁者**。

## 4. 寄存器分配表（新方法 `cfgFix()`，`.registers 8`）

| 寄存器 | 类型 | 用途 | 备注 |
|---|---|---|---|
| v0 | 引用 | `StringBuilder`（CFGT/CFGT3 组串） | 全程引用，禁止改作 int |
| v1 | 引用 | 配置文本（`cfgReadText` 结果，可为 null） | 全程引用 |
| v3 | 引用 | 临时 String（键名 / 拼接常量 / `toString()` 结果） | 独立引用寄存器（血案纪律） |
| v2 / v4 / v5 | int | 解析结果 / 常量 / `append(I)` 参数 | 独立 int 寄存器 |
| v6 / v7 | 未用 | - | 保留 |

- **不使用长整型**（避开 `append(J)` 需 `{v0,v1,v2}` 的寄存器纪律陷阱）。
- `.registers 8` ≥ 实际使用（v0–v5）⇒ 不存在越界。
- 方法**独立成方法**，主方法只加 1 行 `invoke-static`。

## 5. 状态与生命周期

`cfgFix` 不创建任何持久状态：无字段新增、不写文件、不改存档；只读文本 + 写既有 `dg*` 字段 + 追加 2–3 行诊断。字段仍是"每进程一份"，语义与旧链路完全相同（因此**即使旧链路本身没坏，本补丁也只是幂等重写**）。

## 6. 失败与回退

| 现象 | 判定 |
|---|---|
| 日志里**完全没有** `CFGT` 行 | 新代码没被运行（安装/运行链路问题）⇒ 转入"运行的不是这份 dex"专项排查，**不是**游戏逻辑 bug |
| `CFGT tlen=-1` | 文件读失败（权限/路径）⇒ 全部键走默认 |
| `CFGT s=-7,-7,-7,-7,-7` | 读到了文本但**键名匹配失败**（格式/引号/大小写）⇒ 真·解析 bug |
| `CFGT s=<真实数字>` 但 `CFGT3 fp=0` 等 | `sput` 未生效（不可能，除非存在未知写者）|
| `CFGT3` 与 `BOOT2` 一致且等于配置值 | **修复成功** |
| 异常 | `cfgReadText` 内部 `catch Exception` 返回 null；`dWrite` 失败静默 ⇒ 本补丁**不会崩溃**、不会抛异常到游戏主循环 |

## 7. 验收标准（可证伪）

进游戏（等于一次真实启动）后，抓 `files/aircfg_diag.txt`：
1. 必须出现 `CFGT r6d061 tlen=<正数>`、`CFGT s=…`、`CFGT3 r6d061 …` **三行**；
2. `CFGT s=` 五个数应等于配置文件的真实值（测试配置 `prob=33,pin=12345,debug=1,ai_cap=7,ai_build=0` ⇒ `33,12345,1,7,0`）；
3. `CFGT3 fp=33 fpin=12345 fdbg=1 fcap=7 fbld=0`；
4. `BOOT2 dbg=1 prob=33 pin=12345 cap=7 build=0 init=1`。
**不通过**的判据：三行缺失（代码没跑）；`tlen` 正确但 5 个值全 `-7`（键匹配 bug 实锤，转第二轮修）；`CFGT3` 与 `CFGT s=` 不一致（写回被覆盖）。

## 8. 门禁（真实 smali 解释执行 + 反转敏感性）

`toolchain/act/check_r6d061_cfgfix.py`：
- **解释执行** `cfgFix` 的真实 smali（`const-string/const/16/const/4/new-instance/invoke-*/move-result*/if-*/goto/sget/sput/append/toString` 子集），把 `cfgExtractInt`、`cfgReadText`、`dWrite` 用**被测文本替身**接入（不另写规则函数）；
- 真值表 ≥6 条：键全在 / 部分缺 / 全缺 / `text=null` / `prob=-5`（钳到 0）/ `prob=250`（钳到 100）；
- 负样本 ≥3：把哨兵默认改成 0、把 `if-ltz` 改成 `if-gez`、把 `sput` 目标字段换成邻居字段 ⇒ 门禁必须报错；
- **反转敏感性自检**：先在"故意写反"的副本上跑，门禁必须失败（证明门禁能抓方向错）。

## 10. 风险与待办

- **风险1**：若"旧链路确实正常"，那么线上 `prob=0` 的现象说明"运行的 dex ≠ 装机 dex"，本补丁的 `CFGT` 行会缺失 ⇒ 立即转入安装/运行链路专项。
- **风险2**：`updateAll()`/`tryStrikeForAirportP()` 每 tick 调 `demoLoadCfg`（现在每 tick 也调 `cfgFix`）⇒ 每 tick 多一次文件读 + 3 行写盘。**必须限制**：只允许 `tlen>=0` 的行写 3 行；测完立即在下一批改为"仅在启动时自证"（用静态标志位 `cfgFixDone` 一次性）。
- **风险3**：诊断行会让 `aircfg_diag.txt` 快速增长（tick 级）⇒ 抓样窗口要短。
- **待办**：§10 风险2 的一次性开关；baksmali 往返造成的其它类的"格式漂移"需要一次全量 diff 审计（本轮先不动其它类）。
