# 调研 · r6d309 · 卡死修复 v2（科技树自有增量滚动）

## R1 现场证据（r6d308 抓样）
- 冻结时：`nMOV` 持续有（路由旗 i=true）、`nSCM` 持续有（mi=46、f=false）、`nSCW` 展示 `mp=nx=-6466` 长时间不变（采样15条全同）。
- 关键算术：把 nSCM 与 nSCW 交叉对照发现 **st ≈ -6466 - p1**（逐条吻合），即"锚定公式 st=pos-p1"在每帧反复执行、而移动分支写回的值恒等于 pos → **位置被钉死**。

## R2 机制链（原生）
- 拖动走的链路：`actionMove` →（menu_MoveInnerElements 旗）→ `actionMove_MenuInnerElements`：
 - f（updateSliderMenuPosX）== true → 只做锚定：`st = menuPosX - p1`；置 false；**不移动**。
 - f == false → `setMenuPosX(st + p1)`。
- `Menu.setMenuPosX` → `updateMenuPosX`：
 - 值 > posX → 夹回 posX 并 **重新置 f=true**（再武装）；
 - 值 < posX+width-maxSliderX → 夹回该下界并 **重新置 f=true**；
 - 否则直接写入 iNewMenuPositionX。
- 结论：当上述"夹回→再武装→下一帧只锚定"循环进入特定时序（到达右极限附近），会出现**合法路径下的死循环**：每帧只锚定不移动，位置永久钉死——症状与用户"滑到右极限卡死、必须退出重进"完全一致。

## R3 定稿修法（绕开原生锚定）
- 在 `actionMove_MenuInnerElements` 的移动分支（:cond_6b）为**科技树**插入自有路径：
 - 窗口条件：树可见 && activeSliderMenuID==IN_GAME_TECHNOLOGY_TREE（否则走原生）。
 - 自有增量：`delta = p1 - scxL`（scxL 由我们维护；actionDown 时复位 scxOn）；
 - 大跳变保护：|delta|>1200 → 仅重新初始化不滚动；
 - `newPos = getNewMenuPosX() + delta`，**我们先夹**到 `[posX+width-maxSliderX, posX]` 再 `setMenuPosX`（因此 updateMenuPosX 永远走"正常分支"，不再触发再武装循环）。
- 诊断兜底（若仍异常可一击定位）：
 - `nSCA v= nx=`：每次自有路径写入的值与写后目标值；
 - `nSCU in= b= out= p= w= m=`：updateMenuPosX 的入参/分支(0正常,1上夹,2下夹)/落值/几何。
