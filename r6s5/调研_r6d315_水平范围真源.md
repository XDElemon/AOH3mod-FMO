# 调研 · r6d315 · 科技树"水平范围"的真源（按用户指路）

## 结论先行
水平范围（以及你记得的那条"水平滑条"）由 **`Menu.updateScrollable()`** 决定：它遍历菜单全部元素，取 **max(posX+width)** 存入 `iMaxSliderPositionX`（= `getMaxSliderX()`）。滑条长度、拖动可达范围、原生 clamp 全用它。
树的链路：**`applyTopFilter(tab)` → relayoutNodes/relayoutLines → `relayoutDone()` → `updateScrollable()`**——每次开树/切页签都会重算。

## 但为什么范围不对？
`relayoutNodes(tab)` 里对"横排底条元素（Empty 类）"的重设宽度代码，**只在 `tab=="all"` 时执行**；切到分类页签（陆/空/民）时直接跳过 → 那些横排元素保留着 all 页的大宽度 → `updateScrollable()` 算出的 max 仍是 all 页的量级 → **范围虚大、右侧大空白、能滑过头**。
（这段 relayout 是我们在 B5 做"陆/空/民分类重排"时引入的；当时只考虑了 all 页的横排，分类页遗漏。）

## 修法（本批 r6d315）
1. 删掉 "all" 门控 → 横排元素在**所有页签**都按"当前页签列数"重设宽度：
   `width = (iTechnologyWidth+100) × 当前页签列数 + 40`
2. 余量 100→40：最右科技正好"刚过屏幕右沿"一点点。
3. `relayoutDone()→updateScrollable()` 无需改动——它会自动把新宽度吃进 `iMaxSliderPositionX`，滑条与拖动范围同步正确。
4. **推翻 r6d314 的扫描式 clamp**（scxMin/ensureMin 调用已移除，方法/字段暂留为死代码待清）。

## 关键证据
- Menu.updateScrollable 全文（4800+ 行区）：两段 max 累积（Y 高、X 宽）→ iput iMaxSliderPositionX。
- relayoutNodes 反汇编：`rn_empty` 分支 `if tab=="all" → resize; else goto next`（原始 gating）。
- 调用链 3463-3465：relayoutNodes→relayoutLines→relayoutDone（内含 updateScrollable 调用）。
