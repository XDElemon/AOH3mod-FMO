- 批次：**r6d175**（承 r6d174；本批只做"纬度口径修复"，不做 AD-2 雷达开火）

- 结论一句话：**游戏里"半径"有两套口径——画圈走"纬度余弦"、判定走"裸 px 圆"，高纬处差最多 4 倍。**

## 一、根因（两侧代码对照，均已逐字读到）

### 1) 渲染侧：半径的 **Y 半轴**乘了纬度余弦

三处渲染**都**这么做（互相一致，属作者原意）：

| 位置 | 方法 | 做什么 |
|---|---|---|
| `ProvinceDrawArmy.smali:2601-2613` | `drawAirForceRadarIcons` 内联段 | 机场"自身雷达圈"（仅当该省**无**雷达/长波雷达/AAA 建筑时才画） |
| `ProvinceDrawArmy.smali:2794-2806` | 同文件第二处内联段 | 另一条雷达圈绘制路径（**R2 待定：疑似选中/另一入口**） |
| `RadarBitmap.smali:835-847` | `refresh()` | 雷达**建筑**圈（400px / 长波 2400px）画进 `Pixmap`，再整张贴到地图 |
| `ProvinceDrawArmy.smali:341-377` | **`calcRadarRy(I provinceID,I ry)I`** | **上述前两处调用的"正经"纬度换算函数** |
| `ProvinceDrawArmy.smali:378-...` | `calcRadarRy(Province,I)I` | 同上的对象重载 |

换算公式（三处逐字一致，无例外）：

```
f = (centerY_Real - 4300.0f) / 4300.0f      # 4300 = 地图纵向中点
f = f * 1.5707964f                          # π/2
f = cos(f)                                  # ← 纬度余弦
if (f > 1.0f) f = 1.0f                      # 上限
if (f < 0.25f) f = 0.25f                    # 下限  ← 所以最多差 4 倍
```

落点：`rx = R * mapScale`（**不缩放**）｜`ry = R * mapScale * f`（**缩 f**）

- 可见效果：高纬处雷达"圈"被**纵向压扁**成横向拉长的椭圆，最扁时 Y 半径只有 25%。

### 2) 判定侧：纯裸 px 圆，**完全不看纬度**

| 位置 | 内容 |
|---|---|
| `AirForceManager.smali:2855-2875` | `(dx² + dy²) <= radarRange²`（`getCenterX_Real/getCenterY_Real` 之差）⇒ **正圆** |
| `PlayerFogOfWar.smali:463-489` | 同上写法 ⇒ **正圆**，用来决定目标算 "radar" 还是 "airport" |

⇒ **同一个 `radarRange`，画出来是"椭圆（Y×f）"，判定用的是"正圆"**。高纬处（f→0.25）南北方向的实际覆盖可达渲染圈的 **4 倍** ⇒ 正是用户报的"高纬雷达圈的可探测范围远大于渲染出的圈"。

### 3) 旁证：游戏**自己**还有一处"用了 cos 的判定"

| 位置 | 内容 |
|---|---|
| `PlayerFogOfWar.smali:28-47` | **`calcCosK(I y)I`**：同一条 cos 公式，但**先平方再 ×1000 取整** ⇒ 返回"cos² 的千分比整数" |
| `PlayerFogOfWar.smali:1091-1117` | **`planeFogR(F range,I y)I`**：`(int)(range * clamp(cos))` ⇒ **"飞机雷达揭示半径"= R×cos** |

⇒ 作者在**迷雾揭示**这条线上是"乘 cos"的，与渲染一致；**只有"任务探测距离判定"这一处没乘**。
⇒ 所以现状是 **3 票 cos（2 渲染 + 迷雾揭示） vs 1 票裸 px（任务探测）**——"少数派"就是 bug 所在。

## 二、为什么会有两种口径（合理的解释）

`calcCosK` 返回 **cos²×1000** 不是随手写的：它正好为"整数距离平方比较"服务——把 `d² ≤ (R·f)²` 改写成 `d² · 1000 ≤ R² · cosK`（两边同乘 1000，避免浮点）。
⇒ 说明作者**本来就打算**让判定也走纬度口径，只是"任务探测"这一处漏了（或者是后加的代码没跟上）。

---

## 三、两条修法（**需用户拍板，这是设计口径问题**）

### 口径 A：**椭圆口径**（推荐）——判定改成跟画面一致

- 做法：`AirForceManager` 的雷达距离判定（+ `PlayerFogOfWar:480` 那处）**乘同一个 f**（用 `calcCosK` 或我方统一函数），使
  `dx² + (dy/f)² ≤ R²`，与画出来的椭圆**逐像素重合**。
- 视觉：**完全不变**（游戏原本长啥样还长啥样）。
- 玩法：高纬处南北方向雷达**探测距离缩短**（最多缩到 1/4）⇒ 属"修 bug 带来的正确变化"。
- 优点：改的全是"看不见的一致性"；作者的既有约定（cos）被尊重；AD-2 的红圈直接沿用同一函数即诚实。
- 代价：**会改变已有玩法数值**（雷达在高纬的探测范围变小）。

### 口径 B：**正圆口径**——画面改成跟判定一致

- 做法：把三处渲染的 `f` 改成恒等 `1.0`（等价于删掉 cos）⇒ 画真圆。
- 视觉：高纬雷达圈**变大**（南北半径最多 ×4）。
- 玩法：**零改动**（判定原本就是圆）。
- 优点：玩家最直觉（"圈=能打到/能看到"）；不动任何玩法数值。
- 代价：与"迷雾揭示"（`planeFogR` 仍乘 cos）**又产生新的不一致** ⇒ 需要一并把 `planeFogR` 也改成恒等，改动面反而更大（3 渲染 + 1 迷雾）。

### 我的建议
选 **A（椭圆口径）**：改动集中在"判定侧 1~2 处"，视觉零变化，且能把作者已经准备好的 `calcCosK` 用起来；同时 AD 系列从此有唯一纬度函数可依赖（红圈、射程、探测三处同源）。
若你更在意"玩法数值一律不动"，则选 B，但必须把迷雾那条也一起改，否则不一致只是从"渲染 vs 判定"挪到"迷雾 vs 判定"。
